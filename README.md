# SmartCampusAnalytics

Smart Campus Analytics using Python Hadoop Streaming.

The scripts read synthetic campus CSV files and aggregate them with the Hadoop Streaming contract: mappers and reducers use standard input and standard output, and records are tab-separated key/value pairs. A local Python runner on Windows performs the map, sort, and reduce steps. That runner is a simulation of the dataflow. It is not a Hadoop cluster, and this repository does not contain Hadoop job logs.

## Objective and problem statement

Campus services generate several independent logs: Wi-Fi sessions, canteen bills, library gate events, and bus speeds. Each log is too simple for a database report to be the point of the lab, and large enough to show why MapReduce groups records by a key before it aggregates them.

The project answers six operational questions:

1. Which date-hour consumed the most Wi-Fi data?
2. How much data, time, and how many sessions did each access point carry, and what was the average session length?
3. How many units of each canteen item were sold, and what revenue did each item produce?
4. Which pairs of items appear together in the same bill, and in how many distinct bills?
5. Which students stay in the library much longer than the campus average?
6. Which route, on which date-hour, has an average speed below 20 km/h?

The CSV files in `data/` are synthetic. They were generated by `src/generate_data.py` with random seed 42 so the same files can be recreated. They are not exports of real student activity.

## MapReduce architecture and workflow

```text
CSV split
   |
   v
mapper  ---- stdout: key <TAB> value ---->  sort by key  ---->  reducer
   ^                                              |
   |                                              v
stderr diagnostics only                    stdout: key <TAB> aggregate
```

Hadoop Streaming starts an external program for the map task and another for the reduce task. Python is a normal executable here. Hadoop does not import the scripts as a library.

- The mapper reads one record at a time and emits intermediate pairs. It does not compute the final group total, because other mappers may emit the same key.
- The framework partitions, sorts, and groups equal keys. After that sort, every value for one key arrives as a consecutive run.
- The reducer walks that run, keeps a small set of totals for the current key, emits one result when the key changes, and then starts the next key. It does not receive a single semicolon-joined string of all values.

Jobs 4 and 5 need more than one pass because the second question depends on a result of the first:

- Job 4 first builds the item basket of each transaction, then counts pairs across transactions.
- Job 5 first totals each student, then computes one campus-wide average, then keeps students above 1.5 times that average.

The global peak (Job 1) and the global library threshold (Job 5) are correct when one reducer sees every group. `run_all.py` uses one reducer per stage. A cluster command for those stages should set the reducer count to 1, or add another job whose only task is the global comparison.

## Datasets

All timestamps use `YYYY-MM-DD HH:MM:SS` in campus local time, for the teaching week Monday 5 October 2026 through Friday 9 October 2026.

| File | Columns | Rows (excluding header) | What a row means |
| --- | --- | --- | --- |
| `data/wifi_logs.csv` | StudentID, Timestamp, AccessPoint, DataMB, DurationMin | 215 | One Wi-Fi session |
| `data/canteen.csv` | TransactionID, Timestamp, StudentID, Item, Quantity, Amount | 298 | One item line on a bill. Lines that share a TransactionID were bought together. Amount is the line total (price times quantity). |
| `data/library.csv` | StudentID, Timestamp, EntryType, DurationMin | 139 | One gate event. ENTRY carries duration 0. A positive EXIT duration is the visit length. |
| `data/transport.csv` | VehicleID, Timestamp, RouteID, SpeedKmph | 1440 | One speed reading. Routes are R1, R2, and R3. |

The item name `Chai, Cutting` is quoted in the CSV because it contains a comma. The mappers use Python's `csv` module so that comma stays inside the item field.

## The six jobs

### Job 1 — Peak Wi-Fi usage

- Mapper key: `YYYY-MM-DD HH`
- Mapper value: `data_mb,duration_min,1`
- Reducer output: one line per hour, then a `PEAK` line
- Peak rule: largest total `DataMB`. If two hours tie, the earlier hour key is kept.

On this dataset the peak is Wednesday 7 October 2026, 13:00, with 3032.74 MB, 1111 minutes, and 20 sessions.

### Job 2 — Access point utilisation

- Mapper key: access point name
- Mapper value: `data_mb,duration_min,1`
- Average session duration = total duration / session count

`AP-CAFE-01` carries the most data (2213.48 MB across 52 sessions).

### Job 3 — Canteen item frequency

- Mapper key: item name
- Mapper value: `quantity,amount`
- Reducer output: `total_quantity,total_revenue`

Revenue is the sum of the Amount column. The reducer does not multiply price by quantity again. Tea has the highest quantity (84). Biryani has the highest revenue (3760).

### Job 4 — Top co-purchased items (two stages)

Stage 1 groups item names by `TransactionID`. The reducer stores only the current bill, drops duplicate item names, sorts the remaining names, and emits every unordered pair as `left::right` with value `1`. Sorting the two names gives `Samosa::Tea` and `Tea::Samosa` the same key.

Stage 2 sums those 1-values. The sum is the number of distinct transactions that contained the pair. A one-item bill emits no pair. Transaction `T00141` lists Tea twice and Samosa once, and it contributes `Samosa::Tea` once.

The reducer file is sorted by pair name, which is Hadoop key order. `outputs/summary.txt` also ranks the same pairs by count. The most common pair is `Samosa::Tea` in 49 transactions.

### Job 5 — Library usage anomaly (three stages)

Visit rule used everywhere in this project:

- An ENTRY event is an arrival. It is well-formed data and it is not a visit.
- An EXIT event is one visit only when `DurationMin` is numeric and strictly greater than 0.
- Duration is the number stored on that EXIT row. The jobs do not subtract ENTRY time from EXIT time, so a visit cannot be counted twice.
- Student `S021` has a single ENTRY and therefore has no visit total.

Stage 1 emits, for each student, `total_duration,visit_count,student_average`.

Stage 2 (global) adds those totals under one key. The campus average is total duration divided by total visit count. It is the visit-weighted average, not the average of the per-student averages.

Stage 3 keeps a student when `student_average > 1.5 * overall_average`. Equality would not qualify. The filter mapper prefixes keys with `0|` and `1|` so the global record sorts before the student records inside the single reducer.

On this dataset: 3870 minutes over 69 visits, average 56.086957 minutes, threshold 84.130435 minutes. Students S901, S902, and S903 are above the threshold. The other 20 students are not.

### Job 6 — Transport congestion

- Mapper key: `RouteID|YYYY-MM-DD HH`
- Mapper value: `speed_sum,1` (one reading's speed is the partial sum)
- Average speed = sum of speeds / number of readings
- Status is `CONGESTED` when the average is strictly below 20 km/h. An average of exactly 20 is `NORMAL`.

This run produced 180 route-hours: 15 congested and 165 normal. R1 is congested at 08:00 and 09:00. R2 is congested at 17:00. Every R3 12:00 group averages exactly 20.000000 and is `NORMAL`.

## How to run on Windows

Use Python 3.9 or newer. This project was executed with Python 3.12.3. No package install is required.

From the project folder in PowerShell:

```powershell
python src/generate_data.py
python run_all.py
python -m unittest discover -s tests -v
```

`run_all.py` writes every final file under `outputs/` and the Job 4 pair list under `outputs/intermediate/`. It prints `outputs/summary.txt` at the end.

Run one stage without the full driver (the script directory is added to the module path automatically):

```powershell
Get-Content data\wifi_logs.csv -Raw | python src\job1_wifi_mapper.py > outputs\intermediate\job1_map.txt
```

Do not complete that pipeline with Windows `sort`. The system sort does not reliably group the field before the tab, and PowerShell's default encoding can change the stream. `run_all.py` sorts keys in Python and passes the sorted text to the reducer.

On a Linux shell, a single-stage pipe that matches this contract is:

```bash
python3 src/job1_wifi_mapper.py < data/wifi_logs.csv | sort -t "$(printf '\t')" -k1,1 | python3 src/job1_wifi_reducer.py
```

## How to execute the tests

```powershell
python -m unittest discover -s tests -v
```

`tests/test_mapreduce.py` uses `unittest` only. The module regenerates the seed-42 CSVs, then checks:

- mapper keys and values, including the Wi-Fi hour key
- reducer sums and the Job 2 average
- pair generation, duplicate items on one bill, and pair counts
- the strict 1.5× library threshold, and a global average that is weighted by visits
- the strict 20 km/h congestion rule, including an average of exactly 20
- CSV headers, a quoted comma, malformed rows, and empty input
- that a reducer does not merge a key that arrives again after a different key
- that `run_all.py` sorts before the reducer
- end-to-end output of all six jobs against totals computed independently from the CSVs

The last successful run of this command reported `Ran 20 tests` and `OK`.

## Assumptions and limitations

- Records are demonstration data created for the lab.
- Amount in the canteen file is already the line total.
- A library visit is a positive-duration EXIT. Incomplete ENTRY-only events are ignored in the averages.
- Item names are case-sensitive and must not contain `::`. Route IDs must not contain `|`.
- The `PEAK` line and the anomaly decision assume one reducer. Several reducers would each see only a partition of the keys.
- Numeric fields are written with six decimal places. The anomaly comparison uses the summed floats, and the printed threshold is that comparison value.
- The local runner holds one stage's intermediate pairs in memory while it sorts them. That is acceptable for these files (the largest is 1440 transport rows) and is a property of the simulator.
- Mappers and reducers themselves keep only the current key's totals, plus the current canteen basket in Job 4 stage 1.
- Empty input produces empty stdout and exit code 0. Malformed rows are counted on stderr and omitted.
- No screenshot in this project claims that Hadoop itself was executed.

## Performance: combiners, shuffle, partitioning, and skew

**Combiners.** A combiner is a local pre-aggregation on a mapper's output. It is valid only when partial results have the same shape as mapper values and the reducer can combine those partials. Sums of data, duration, quantity, revenue, speed, and counts have that shape. The checked-in reducer scripts also divide, attach `CONGESTED`/`NORMAL`, or emit `PEAK`. Those scripts must stay reducers. A combiner for Job 1 would emit `data_sum,duration_sum,count` and would not emit `PEAK`. Using the Job 1 reducer binary as `-combiner` would publish several local peak lines and then sum them incorrectly.

**Shuffle traffic.** Shuffle moves mapper output across the network, sorted by key. Job 4 stage 1 moves one item name per canteen line, then stage 2 moves one record per pair occurrence. Pair generation expands a basket: a bill of three distinct items becomes three pair records, a bill of one item becomes zero. Job 5 stage 1 shrinks every student's visits into one record, so the global job shuffles 23 rows, not the raw gate log. Emitting `duration,1` instead of the raw CSV line is what makes that reduction possible.

**Partitioning.** The default partitioner hashes the whole key and sends that hash to a reducer. Job 6's key is route plus hour, so two hours of route R1 usually land on different reducers. That matches this job, because each route-hour is independent. A custom partitioner on route alone would be needed only if one reducer had to see every hour of one route. Job 5's filter deliberately forces a total order with `0|` and `1|` prefixes and a single reducer, because the threshold is a global number.

**Data skew.** A skewed key forces one reducer to do a disproportionate share of the work. In this sample the heavy keys are visible and still small: the Wi-Fi peak hour has 20 sessions against 2–4 in a typical hour, and `Samosa::Tea` appears in 49 bills against 6 for `Maggi::Tea`. On a real log those ratios can become millions of values for one key. Useful responses are a combiner (so the popular key ships a partial sum), a salt that splits a hot key across reducers and then merges it in a second job, and more reducers for keys that are not part of a global threshold. Salting the Job 5 `ALL` key would break the single global average unless a later job removed the salt. The congestion labels in this dataset are balanced on purpose: every route-hour has the same number of readings, so the slow hours are slow because of the speed values, not because they contain more rows.

## Adapting the scripts for Hadoop Streaming

Copy the input CSVs to HDFS. Ship `streaming_io.py` together with the mapper and reducer, because the scripts import it. The scripts already speak the Streaming protocol, so the map and reduce logic does not change.

Example for Job 1, with one reducer so the `PEAK` line sees every hour:

```bash
hadoop jar "$HADOOP_HOME/share/hadoop/tools/lib/hadoop-streaming-"*.jar \
  -files src/streaming_io.py,src/job1_wifi_mapper.py,src/job1_wifi_reducer.py \
  -mapper "python3 job1_wifi_mapper.py" \
  -reducer "python3 job1_wifi_reducer.py" \
  -input /user/campus/wifi_logs.csv \
  -output /user/campus/job1_peak_wifi \
  -numReduceTasks 1
```

Job 4 needs two submissions. The input of stage 2 is the HDFS output directory of stage 1. Delete an output directory before repeating a job, because Hadoop refuses to overwrite it.

Job 5 needs three submissions:

1. `job5_stage1_mapper.py` and `job5_stage1_reducer.py` on `library.csv`
2. `job5_global_mapper.py` and `job5_global_reducer.py` on the stage 1 output, with one reducer
3. `job5_filter_mapper.py` and `job5_filter_reducer.py` on both the stage 1 output and the global output, with one reducer

Pass multiple inputs by repeating `-input`, or copy the two small outputs into one HDFS directory first.

Job 6 can use more than one reducer. Each route-hour is complete inside its own key, and the congestion label does not depend on a global statistic.

After a real cluster run, copy the part files back and compare them with `outputs/`. Until that is done, the evidence of execution is the local `outputs/` directory and the unittest result.
